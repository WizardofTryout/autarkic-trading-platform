# **Technical Specification: AI-Strategy Engine & Custom Charting (v1.2)**

Goal: Complete independence from proprietary libraries (TradingView) and implementation of an AI-assisted translation for trading strategies.  
Priority: High.  
Status: Updated based on Dev Team Feedback (2025-12-05).

## **✅ 1\. DECISIONS & CLARIFICATIONS (BASED ON TEAM FEEDBACK)**

To ensure zero ambiguity, here are the explicit decisions regarding your questions:

1. **Charting Technology:**  
   * **Decision:** **Stick with D3.js.**  
   * **Reasoning:** It is already integrated (D3Chart.tsx) and offers sufficient flexibility for our needs (FVG, Trendlines) without adding the overhead of a new library like ECharts.  
2. **AI-Transpiler API-Key Management:**  
   * **Decision:** **User-Specific Keys.**  
   * **Implementation:** The backend must fetch the user's specific Gemini API key from the user\_api\_keys table. Do **NOT** use a system-wide environment variable (os.getenv) for user actions.  
3. **Strategy Execution Environment:**  
   * **Decision:** **Use strategy-engine Container.**  
   * **Implementation:** All Python code generated by the AI must be sent to the isolated strategy-engine service (Port 8001\) for execution. Do **NOT** execute user code in the main backend service.  
4. **Backtest Integration:**  
   * **Decision:** **Full Stack Implementation (Phased).**  
   * **Phase 1:** Frontend integration (sending Python code to backend).  
   * **Phase 2:** Full Backend Engine (Loading OHLCV from DB, executing signals, calculating PnL).  
5. **Database Schema:**  
   * **Decision:** **Add requested fields.**  
   * **Required:** Add type (ENUM: 'INDICATOR', 'STRATEGY') and compiled\_at (TIMESTAMP) to the strategy table.  
6. **Fair Value Gaps (FVG):**  
   * **Decision:** **Frontend First.**  
   * **Phase 1:** Implement visualization in D3.js using Mock Data from the backend.  
   * **Phase 2:** Implement the actual detection logic in Python in the backend.

## **3\. Strategy: Pine Script Transpilation via AI (LLM)**

Instead of writing a custom parser for Pine Script, we use the system-integrated LLM (Gemini/AI Sentinel) as a **Transpiler**.

### **The Workflow**

1. **Input:** User writes Pine Script in the Frontend Editor.  
2. **Process:** The Backend sends this code \+ System Prompt to the AI Service.  
3. **Output:** The AI returns valid Python code based on our internal StrategyEngine (Pandas).  
4. **Execution:** The Python code is sent to the existing **Strategy Engine Service** (Container strategy-engine, Port 8001\) for isolated execution.

## **6\. UX/UI Implementation: The "No-Copy-Paste" Workflow**

Problem: The user must not be required to manually copy the Python code generated by the AI.  
Solution: "Auto-Injection" into a secondary editor tab.

### **UI Layout Instructions (Frontend)**

The "Pine Script Editor" area (Left column in Strategy Builder) is expanded into a **Tab System**:

* **Tab A: "Source (Pine Script)"** (The existing editor)  
* **Tab B: "Engine (Python)"** (New, initially empty or Read-Only)

### **Functional Flow (Step-by-Step)**

1. **Trigger:** User clicks on a new button **"Generate Strategy Engine"** (next to "Save").  
2. **Transpilation:** Backend (AI) generates the Python Code.  
3. **Auto-Injection:**  
   * The Frontend receives the Python string.  
   * The Frontend **automatically** switches to **Tab B (Engine)**.  
   * The code is injected directly into the editor of Tab B.  
4. **Editability:** The user can manually adjust the Python code in Tab B.  
5. **Strategy Tester Connection:**  
   * When the user clicks **"Run Backtest"**, the system now **always** uses the code from **Tab B (Engine)**.  
   * It sends this code to the strategy-engine container for execution.

### **Save Logic & Database**

When clicking "Save Strategy", **both** code fragments must be stored in the database.

**Updated Database Schema Requirements:**

* strategy.source\_code (Pine Script)  
* strategy.python\_code (The generated/edited Python Code)  
* strategy.type (ENUM: INDICATOR or STRATEGY)  
* strategy.compiled\_at (TIMESTAMP, nullable)

## **7\. Extension: Indicators vs. Strategies (Composition)**

### **7.1 Data Model Extension (Type Separation)**

When saving or creating, the type must be explicitly set:

* **Type INDICATOR**:  
  * Output: A numeric series (e.g., RSI curve).  
  * Behavior in Tester: Can **NOT** be backtested alone.  
  * UI: Can only be "overlaid on the chart".  
* **Type STRATEGY**:  
  * Output: signal\_long / signal\_short Booleans \+ StopLoss/TakeProfit Prices.  
  * Behavior in Tester: Can be backtested (PnL, Drawdown).

### **7.2 The "Strategy Composer" Workflow**

**User Story:**

1. User opens "Strategy Builder".  
2. Selects in menu: **"Combine Indicators"**.  
3. UI shows Dropdowns for Indicator A and B.  
4. User defines logic in text form (Prompt).  
5. **AI Action:** The AI generates the Python code.  
6. **Result:** The whole thing is saved as a new entry of type STRATEGY.

**Instruction to Frontend:**

* The "Save" dialog needs a Radio Button: \[ \] Save as Indicator vs \[ \] Save as Strategy.  
* If Indicator is selected, the "Backtest" button in the Tester is disabled (greyed out).
